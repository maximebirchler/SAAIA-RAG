# Audit du runtime de déploiement — 26 octobre 2026

État : **runtime Docker de déploiement non qualifié**. La chaîne Windows a des preuves réelles d’ingestion et de publication, mais elles ne constituent pas une validation des images Docker prévues en production. Cet audit est en lecture seule : aucun démarrage, installation, build, requête HTTP, accès serveur, opération Git ou lecture de `.env`/secret. Les empreintes des sources lues et les observations matérielles sont dans `runtime-audit-observations.json`.

## Ce qui est réellement acquis

Les résumés `worker-full-e5-lifecycle-final-v2/execution-result.json` et `worker-recipe-e5-final-v3/execution-result.json` de la campagne précédente annoncent chacun `passed=true`, `executed=true`, `canonicalRowsSeeded=false`, `paidProviderCalls=0`, `sqlPublicationValidated=true`, `vectorStorePublicationValidated=true`, `canonicalSearchValidated=true` et un arrêt du backend/PG possédés avec zéro job actif. Les publications couvrent 12 PDF synthétiques puis le livre réel de 36 pages. Le cycle de vie dispose d’une preuve séparée pour le corpus synthétique.

Ces exécutions utilisent un backend .NET natif Windows, PostgreSQL Windows, Qdrant Windows 1.20.0, Docling installé dans un environnement Python local et **un adaptateur Transformers CPU**, avec de vrais poids E5. Leurs profils désactivent scanner/watcher, OCRmyPDF/Tesseract historiques et reranker ; ils utilisent un seul worker et une collection neuve. `vectorValidated=false` reste explicitement déclaré : une publication correcte n’est pas une validation générale de pertinence sémantique. Aucun de ces résultats n’atteste le binaire TEI, le conteneur backend Linux, le cache Docling dans l’image, les droits des volumes Linux ni les chemins OCR historiques.

## Disponibilité locale constatée

- Windows 11 Famille x64, build 26200 ; i7-14700F, 20 cœurs / 28 processeurs logiques ; environ 31,76 GiB de RAM physique. Le relevé ponctuel de mémoire libre est d’environ 14,3 GiB et n’est pas une réservation disponible pour Docker.
- RTX 4060 : `nvidia-smi` annonce 8 188 MiB de VRAM, pilote 595.95. Le chemin qualifié et les services Docker proposés sont CPU : ce GPU n’est pas un prérequis pour la première qualification.
- Aucune commande `docker` ou `podman` dans le PATH ; Docker Desktop et docker.exe absents des chemins standards examinés. Aucun service Docker observé.
- `wsl.exe` existe, mais `--status` et `--list --verbose` indiquent que WSL n’est pas installé ; aucun paquet WSL Appx ni distribution enregistrée observés. La fonctionnalité VirtualMachinePlatform est activée (InstallState 1), Windows-Subsystem-Linux désactivée (InstallState 2), `vmcompute` arrêté.
- `HypervisorPresent=true` alors que `VirtualizationFirmwareEnabled=false`. Ces deux propriétés ne justifient **pas** une conclusion « virtualisation BIOS désactivée ». La capacité WSL2 doit être contrôlée lors de la préparation autorisée.

Le blocage local certain est donc l’absence de moteur Docker/WSL fonctionnel. Le présent audit n’a rien installé ni activé. Aucun état du serveur distant n’a été interrogé.

### 1. Identités signées et images peuvent diverger

Le template signé fixe les révisions TEI/Qdrant historiques (`infra/config/deployment.config.prod.template.json:20,26`), tandis que compose permet `TEI_IMAGE`, `QDRANT_IMAGE` et leurs révisions en environnement. `_common.ps1:370–374` remplace modèle/révision du modèle, mais ne substitue pas les deux révisions runtime fixes du template. En production la configuration signée est ajoutée après les sources initiales et prime sur leurs valeurs (`Program.cs:6–13`, `Security/SignedConfigLoader.cs:84–85`). Changer seulement l’image ou la variable d’environnement peut ainsi conserver une identité déclarée inexacte.

De même, `_common.ps1:348` génère `ChunkMaxWords=220` par défaut, contre 200 dans compose et dans les preuves Windows. Ce n’est pas un détail d’affichage : il modifie les chunks et les entrées d’embeddings.

La révision backend vaut `unknown` par défaut dans le Dockerfile et compose (`backend/SAAIA.Backend/Dockerfile:36–37`, compose:128). Or la provenance canonique est activée par défaut et rejette `unknown` (`IngestionProvenanceConfiguration.cs:12–20`, `ReadyEndpoints.cs:261–282`). Le script de déploiement distant fournit des empreintes de sources (`deploy-remote-backend.ps1:211–214,370`), mais l’installation générique ne les calcule pas. Il faut donc imposer une identité réelle avant le build, puis conserver l’empreinte de la DLL effectivement chargée dans le conteneur. Ne pas étiqueter cette DLL avec l’empreinte de la DLL Windows.

### 2. La reproductibilité du build n’est pas fermée

PostgreSQL, SDK .NET et runtime .NET utilisent des tags mobiles (`postgres:16`, `sdk:8.0`, `aspnet:8.0`). Les paquets apt OCR sont installés sans version figée (`backend/SAAIA.Backend/Dockerfile:29–34`). Le Dockerfile ne copie ni le `global.json` qui exige SDK 8.0.420 ni `Directory.Build.props` avant restore/publish ; ce dernier n’est pas admis par la sélection actuelle du contexte. Cela ne prouve pas un échec de compilation, mais le contrat de compilation diffère de celui testé dans le checkout.

La source sidecar est copiée sur une base Docling épinglée, ce qui est un bon début. Il manque encore, pour cette qualification, l’observation de ses paquets réels, les empreintes de ses modèles/cache, la révision du wrapper et l’identité de l’image résultante. L’attestation existante vérifie les versions déclarées lorsqu’elles sont présentes dans la réponse (`DoclingExecutionMetadataPolicy.cs:6–29`) ; elle ne remplace pas une observation de l’image réelle.

### 3. Embeddings : comportement long et harnais différents

L’adaptateur Windows refuse plus de 512 tokens sans tronquer (`local_embeddings.py:62–68`) ; compose lance TEI avec `--auto-truncate` (prod:42, compose simple:45). Il faut mesurer ce que reçoit le moteur, la limite effectivement appliquée et le nombre d’entrées tronquées. Le texte canonique peut rester intact dans SQL tout en étant partiellement représenté par son vecteur. Le backend ajoute les préfixes E5 `query:` / `passage:` (`Rag/TeiClient.cs:215–234`) ; ces deux formes doivent être exercées sur TEI, y compris en batch et sur les cas longs, multilingues et contenant chiffres/signes.

Le harnais actuel ne peut pas simplement déclarer TEI conforme : `Read-OwnedEmbeddingProfile` exige `adapter=transformers_cpu` et `/info` au format spécifique du validateur (`OwnedIngestionConfig.ps1:93–110`, `probe-local-vectors.py:44–59`). Le runner démarre aussi un backend/PG natifs et impose des endpoints loopback. Une qualification de conteneurs exige un adaptateur d’attestation et un bootstrap Docker dédiés ; falsifier le profil TEI ou relâcher ces gardes rendrait les preuves trompeuses.

### 4. Démarrage hors ligne, ressources et faux succès

La campagne Windows fixe `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, les répertoires de modèles et `remote_services=false`. Le compose Docling ne fixe ni ces barrières ni un volume de cache explicite. L’image peut déjà contenir des modèles : aucune requête extérieure n’est affirmée ici. Il faut néanmoins prouver un démarrage et une conversion avec egress réseau refusé, après un provisionnement public séparé et tracé. Ce provisionnement n’autorise aucun envoi documentaire ni achat.

Docling reçoit une limite 14 GiB/8 CPU et le reranker 8 GiB/6 CPU, auxquels s’ajoutent backend, TEI, Qdrant et PG. Les 31,76 GiB de la machine ne garantissent pas que cette somme soit exploitable avec Windows et les autres processus. Prévoir un budget RAM/CPU explicite et mesurer pic RSS, limites Docker, OOM/restarts, temps froid/chaud et files d’attente. La première qualification peut isoler l’ingestion et désactiver le reranker, puis qualifier séparément l’offre qui l’active.

`install.ps1:210–215` émet seulement un avertissement si `/ready` ne répond jamais, sans échec explicite ; une sortie du script sans exception ne doit donc pas devenir une preuve d’installation réussie. De plus, les runbooks historiques M4 contrôlent surtout `/ready`, signature et bundles (`06_M4_DoD.md:38–57`), sans preuve de bout en bout OCR/canonique. La nouvelle acceptation doit échouer si les états ou artefacts requis sont absents, même avec HTTP 200 sur une santé superficielle. Le template signé contient encore une enveloppe externe historique de 25 USD et des tarifs/ledger nommés Terra (`deployment.config.prod.template.json:88–96`). Ce n’est ni une autorisation pour cette mission ni un solde fournisseur. La qualification ingestion doit conserver cette capacité désactivée ; une éventuelle mission LLM ultérieure nécessitera sa propre configuration autorisée, sans recycler ces montants.

## Protocole réel local proposé

1. **Préparer la capacité de conteneurisation sous contrôle de l’opérateur.** Vérifier WSL2/virtualisation et disque libre ; installer/activer seulement après décision explicite. Aucun lancement de ce rapport ne l’a fait. Conserver le serveur existant hors périmètre.
2. **Geler une pile cible.** Choisir un seul compose de référence, les digests d’images, paquets, révisions de modèles et hash des poids ; résoudre les écarts 1.10/1.16/1.20, TEI et Docling sur une base de compatibilité testée. Générer une configuration signée qui correspond à ces identités. Fermer les workers LLM et les transmissions externes : `AdvancedAnalysis` désactivé, fournisseur désactivé, CapabilityB automatique désactivée, absence de credentials fournisseur dans le conteneur.
3. **Créer une installation de qualification isolée.** Nouveau nom de projet Compose, racine de données, volumes/réseau, DB, collection Qdrant et ports élevés loopback. Refuser tout chemin usuel, volume existant ou collision. Ne pas utiliser le projet Compose habituel, le port PostgreSQL 5432 ou `/opt/saaia`. Conserver manifeste d’ownership, ID des conteneurs, dates de création et labels. Aucun seed de pages/unités/chunks.
4. **Provisonner puis observer.** Construire/télécharger uniquement les artefacts publics nécessaires dans un scope neuf, puis enregistrer image ID/digest, OS/architecture, SDK/runtime, paquets Docling/OCR et modèle réel. Refaire le démarrage avec egress refusé ; observer la signature, les migrations et la provenance dans `/ready`, les quatre sentinelles FTS réelles, les compteurs de santé Docling, TEI et Qdrant. Vérifier les droits read/write des seuls volumes possédés et le comportement sur caractères Unicode et noms longs.
5. **Tester TEI réellement.** `/v1/embeddings` sur `query:` et `passage:`, dimensions, cardinalité/index, valeurs finies non nulles, batch, mauvaise requête et modèle déclaré. Vérifier troncature/413 et éventuelles limites différentes ; enregistrer versions/tokenizer/config/poids, sans inventer des champs `/info`. Rejouer l’anti-vecteurs constants, les permutations de classement et une marge explicite via Qdrant. Ce témoin reste distinct de l’acceptation documentaire.
6. **Ingestion des corpus figés.** API d’enqueue sur la source PDF hashée, puis vrai worker jusqu’à terminal. Rejouer les 12 cas synthétiques puis le manifeste réel enrichi à 16 faits. Contrôler le brut physique, la structure/tableau/ordre, les blocs canoniques et leurs ancres, les checksums UTF8 des quatre tables, la publication atomique, l’ID de point dérivé du chunk et du plan actif, la recherche exacte/sparse/dense et la lecture de source correspondante. Inclure les valeurs signées/décimales/négations, scans FR/EN, pages mixtes, tableaux et titres de navigation. Aucun LLM requis.
7. **Vie réelle et panne bornée.** Changement du fichier, réingestion, suppression/recréation, annulation queued/running avec ACK, redémarrage du worker/conteneur, expiration/reprise de bail, refus des anciens points et preuve qu’aucune génération annulée n’est faussement classée en cours. Observer séparément la fin du calcul Docling amont ; l’annulation d’une requête n’en prouve pas l’arrêt. Tester la perte temporaire de TEI/Docling/Qdrant et la restauration sans publication partielle.
8. **Clôture et qualification.** Zéro job actif, aucun appel LLM, zéro ressource possédée orpheline ; preuve des conteneurs et ports après arrêt, données/preuves conservées selon politique. La purge se limite aux ressources dont l’ownership est prouvé. Aucun `docker system prune`, aucun `down -v` d’un projet non isolé, aucune suppression des sources ou anciennes preuves sur la base de leur nom. Décision de qualification séparée des preuves de test, avec limites de performance et contrats effectivement validés.

## Critères de décision

La prochaine étape logique est d’obtenir un runtime local capable d’exécuter la pile Docker ciblée, puis de créer ce harnais isolé et de rejouer l’ingestion. Il n’est pas nécessaire d’acheter des crédits LLM ou de solliciter un serveur distant pour ce travail. Un succès Windows garde sa valeur pour le code et les documents déjà testés ; une réussite Docker devra apporter de nouvelles preuves portant sur les composants réellement distribués.

Restent non vérifiés ici : images et paquets réellement installés sur le serveur, ressources du serveur, disponibilité du cache dans les images, possibilité actuelle d’un démarrage Docker local, performance sous limites, conformité des digests dans un registre et comportement réel des services Docker. Aucune connexion serveur ni requête de registre n’a été faite.
