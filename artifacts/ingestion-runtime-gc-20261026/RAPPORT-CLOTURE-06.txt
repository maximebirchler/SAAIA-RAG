SAAIA — clôture de la qualification ingestion, 26 octobre 2026
Ce rapport porte sur les travaux réalisés depuis le précédent envoi de 10:27 UTC. Le rapport détaillé complet est dans le dépôt : artifacts/ingestion-runtime-gc-20261026/RAPPORT-FINAL-QUALIFICATION-INGESTION.md.

RÉSULTAT : le périmètre d’ingestion exercé est qualifié sur la pile Linux CPU exacte, en environnement Production avec configurations réellement signées. Les cinq nouveaux environnements de campagne passent. Il n’y a eu aucun appel de LLM payant et aucun nouveau test du planning. Le produit reste TESTE_NON_APPROUVE : l’ingestion qualifiée ne suffit pas à approuver toutes les réponses du RAG.

1. Le dernier vrai défaut trouvé était le démarrage à froid de Docling. Trois jobs avaient échoué en HTTP 502 à 10:20:39/41/43 UTC, alors que son service interne n’a commencé à écouter qu’à 10:20:46. Le bootstrap de test attendait seulement des containers « running ». Ce n’était donc pas un échec de compréhension du modèle : le moteur de conversion était encore indisponible. Les échecs et timestamps ont été conservés.

2. J’ai corrigé les deux niveaux utiles. Le bootstrap vérifie maintenant la santé réelle de PostgreSQL, TEI, Qdrant et Docling avant de créer le backend. Pour Docling, la réponse doit notamment confirmer upstream=true. Le client Docling reprend aussi les erreurs transitoires clairement reconnues : cinq tentatives maximum, pauses 1/2/4/8 secondes, sous un délai global unique. Il réutilise le même fichier ouvert et reconstruit chaque requête ; erreurs permanentes et réponses ambiguës restent terminales. Les nouvelles sondes indiquent les tentatives, raisons et durées sans exposer document ou secret.

3. La preuve avant correction donnait 8 échecs et 12 témoins verts. Un premier passage après correction a donné 25 succès et 1 échec de fixture Windows : File.Move ne remplaçait pas un fichier encore ouvert. Le comportement de File.Replace a été vérifié séparément et la fixture corrigée, sans assouplir le produit. Les 26 cas passent finalement sur Windows ET Linux. La nouvelle campagne réelle de démarrage à froid attend effectivement la disponibilité avant le démarrage du backend et termine correctement. Une panne TCP réelle injectée n’a pas été exécutée : les 26 tests de reprise utilisent un transport HTTP déterministe, et le parcours réel est une preuve distincte.

4. Toutes les suites finales ont été relues : 5 323 tests .NET réussis, zéro échec, avec 2 cas Windows non exécutés ; 350 tests PostgreSQL isolés réussis, zéro échec, avec 2 anciens scénarios runtime non exécutés ; 180 tests Python d’ingestion réussis. Les deux cas Windows sont précisément l’OCR externe et les chemins Linux : ils ont été réellement exécutés à part sous Linux, chacun 1/1 PASS. Les compteurs ne sont pas additionnés entre campagnes qui se recouvrent. Les sources sont stables et les suites Unit/PG emploient les mêmes assemblies finales.

5. La pile réelle a ingéré les 12 PDF Gold et le livre de recettes 36 pages avec le vrai worker, Docling, TEI, PostgreSQL et Qdrant. La publication est vérifiée dans SQL et dans le stockage vectoriel. Ensuite, 90 faits Gold et 16 faits recettes ont tous été retrouvés puis lus par les API avec les bonnes identités de document, page, révision, plan et chunk. Ce 106/106 démontre ce parcours sur ces annotations ; il ne prouve ni tous les types de questions, ni le classement du canal vectoriel seul, ni encore le raisonnement du planning.

6. Les trois profils automatiques passent : scanner seul, watcher seul, puis scanner+watcher. Le scénario combiné a réellement observé deux jobs running avec deux propriétaires distincts dans le même snapshot SQL ; ce n’est pas seulement workerCount=2 dans une configuration. Les limites sont conservées : le scanner seul n’a observé qu’un job simultané ; le watcher seul confirme le fichier manquant et conserve la publication, sans qualification de la suppression finale après grâce dans ce profil. La course « fichier revenu pendant une suppression » n’a pas été capturée automatiquement, car le delete a terminé avant l’observation. Les 16 cas PostgreSQL causaux associés passent, mais je ne les rebaptise pas en capture runtime de cette course.
